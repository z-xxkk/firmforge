# 工具与 MCP 框架（计划，待负责人审核）

起草：Claude Code，2026-10-26。这份是 [gap_rules.md](gap_rules.md) 第一、二节的展开版，以这份为准。★ 是我定的，不同意可以改。

---

## 0. 一句话

**给 Agent 装上"手"（工具），手的接口用业界标准（Function Calling 和 MCP），这样 Agent 能自己去查资料、试编译；别人的工具能插进来，我们的判定器也能插到别人那里去。**

## 1. 先把三个词说清楚

| 词 | 打个比方 | 在我们这里具体是什么 |
|---|---|---|
| **工具** | Agent 的手。现在的 Agent 只有"嘴"（只能写文字），写完交卷才知道对不对 | 一个能被调用的功能，比如"查知识库""编译一下试试" |
| **Function Calling**（函数调用） | Agent 说"帮我拿一下扳手"的**固定说法**。DeepSeek 接口规定了这句话的格式：工具名 + 参数 | 我们把工具清单随请求发给 DeepSeek；它在思考中途回一个"我要调用 X，参数是 Y"；平台去执行，把结果塞回对话，它接着想 |
| **MCP**（模型上下文协议） | 工具界的 **USB-C 插座标准**。按这个标准做的工具，任何支持 MCP 的 AI 软件都能直接插上用 | 两个方向：①我们的 Agent 能插上别人按 MCP 做的工具（我们当"客户端"）；②别人的 AI 软件能插上我们的判定器（我们当"服务端"） |

Function Calling 管的是"**模型和平台**之间怎么说要用工具"；MCP 管的是"**平台和工具**之间怎么接"。两者不冲突，一个在上、一个在下。

## 2. 整体结构

```
                 ┌──────────────── FirmForge 平台 ────────────────┐
                 │                                                │
 DeepSeek 模型 ◄─┼─► 工具调度员 ──► 工具箱（登记所有工具）          │
 （思考，决定要  │   · 把工具清单发给模型   ├─ 内置工具（Python 写的）  │
  不要调工具）   │   · 收到"要调用"就执行   │   kb_search              │
                 │   · 结果塞回对话         │   compile_check          │
                 │   · 管次数、超时、截断   │   list_interface         │
                 │   · 每次调用记一笔       │                          │
                 │                          └─ MCP 客户端 ──────────────┼──► 外部 MCP 服务
                 │                              （按需启动、发现工具）   │    例：fetch（抓网页）
                 │                                                │
                 │   MCP 服务端（firmforge mcp）◄──────────────────┼──── Claude Code、Cursor 等
                 │     · list_tasks / verify_c_module / kb_search │    别的 AI 软件
                 └────────────────────────────────────────────────┘
```

- **工具箱**只有一个：内置工具和外部 MCP 工具登记在一起。Agent 看到的是一张统一的工具清单，分不出哪个是内置、哪个来自 MCP。
- **工具调度员**是唯一和模型打交道的地方，所有规矩（次数、超时、隐藏测试隔离）都在这一处执行，不会漏。

## 3. 一次工具调用的完整经过（举例）

pdu 模块第 1 次没通过，coder-fast 第 2 次动手：

| 步 | 谁 | 发生了什么 |
|---|---|---|
| 1 | 平台 | 按任务单格式（见 gui_sketch.md 第六节）组织好要求，连同 coder-fast **被允许用的工具清单**一起发给 DeepSeek |
| 2 | 模型 | 思考后回："调用 `kb_search`，参数 `{"query": "Modbus 读寄存器 数量范围"}`" |
| 3 | 工具调度员 | 检查：这个工具 coder-fast 能用吗？参数合法吗？这次生成里已经调了几轮？都没问题 → 执行 |
| 4 | 工具 | 在知识库里检索，返回最相关的 3 段（超过 4000 字就截断并注明） |
| 5 | 工具调度员 | 把模型这一轮的完整回复（**含思考内容**，DeepSeek 规定必须回传，否则报错）和工具结果放回对话，再请求一次；同时发出事件 `tool_called`，界面上出现一行蓝色记录 |
| 6 | 模型 | 写好草稿后，回："调用 `compile_check`，参数 `{文件内容}`" |
| 7 | 工具 | 在临时目录里用主机 gcc 和 arm-none-eabi-gcc 编译，返回"都通过"或报错 |
| 8 | 模型 | 不再调工具，直接交卷 → 进入正常的判定和修正循环 |

如果模型在一次生成里调了 5 轮还不交卷，第 6 次请求**不带工具清单**，要求它直接交卷。

## 4. 工具清单

### 内置工具（我们自己写，Python 标准库实现）

| 工具 | 参数 | 返回 | 为什么需要 |
|---|---|---|---|
| `kb_search` | `query`：要查的话 | 知识库里最相关的 3 段，每段注明出自哪篇 | 现在知识库只在升级第 1 级时由平台塞给 Agent；有了工具，Agent 在任何时候觉得需要都能自己查 |
| `compile_check` | `files`：文件名 → 内容 | 主机编译、交叉编译两层的结果和报错原文 | 让 Agent 交卷前自己发现语法错误和警告，少浪费一轮完整的判定和修正 |
| `list_interface` | 无 | 本模块要实现的函数原型、依赖模块提供的函数、公共头文件全文 | 并行写代码时最常见的错误是接口对不上（DECISIONS 第 33 条），让 Agent 随时能核对 |

### 外部 MCP 工具（举例，★ 首批只接 1 个用来演示）

| 服务 | 来源 | 做什么 | 默认 |
|---|---|---|---|
| `fetch` | MCP 官方参考服务器之一（modelcontextprotocol/servers 仓库的 fetch） | 抓取网页并转成文字，Agent 可以去读芯片手册网页 | 关闭；开启后每次调用前问你；评测时一律关闭 |

外部工具在 Agent 那里的名字是 `mcp__服务名__工具名`（例如 `mcp__fetch__fetch`），和 DeepSeek Harness 的命名规则一致，一看就知道是外部的。

## 5. 谁能用什么

写在每个 Agent 的定义文件里（`agents/*.toml`），不写死在代码里：

```toml
name = "coder-fast"
role = "coder"
skills = ["按需求写嵌入式 C 模块", "按诊断修改代码"]
tools = ["kb_search", "compile_check", "list_interface"]
memory = { experience = true, knowledge = true }
```

| Agent | ★ 默认工具 | 理由 |
|---|---|---|
| 编码（coder-fast / coder-strong） | 3 个内置全给 | 写代码最需要查资料、试编译、对接口 |
| 测试（tester） | `kb_search`、`list_interface` | 写测试要知道接口；**不给 `compile_check`**，因为测试 Agent 不应该看到实现代码，而编译测试离不开实现 |
| 诊断（diagnoser） | `kb_search` | 判断错误原因时查资料 |
| 规划（planner） | `kb_search` | 拆模块时参考同类协议的写法 |
| 审查（reviewer） | 无 | 只提意见，用不上 |
| 需求分析（analyst，界面方案选 B 才有） | `kb_search` | 追问需求时参考领域知识 |

界面上在"Agent 团队"里勾选，改的就是这个文件。写了不存在的工具名，加载时报错并指出哪个文件。

## 6. 安全和公平的规矩

| 规矩 | 怎么做到 |
|---|---|
| **任何工具都碰不到隐藏测试** | `compile_check` 在一份临时副本里跑，副本不含 `hidden_tests/`；只跑第 1、2 层。补一个单元测试：故意让工具去找隐藏测试，必须找不到 |
| 一次生成最多 5 轮工具调用 | 工具调度员计数，用完后不再给工具清单 |
| 不会被卡死 | `compile_check` 超时 60 秒；外部 MCP 工具超时 30 秒；超时作为"工具出错"返回给 Agent，不中断运行 |
| 返回内容不会撑爆上下文 | 每次结果最多 4000 字，超出截断并注明 |
| 外部工具不乱用 | 默认关闭；开启后默认"调用前问我"（MCP 规范要求宿主在调用工具前取得用户同意）；评测模式下外部工具一律关闭，保证结果可复现 |
| 密钥不泄露 | 外部 MCP 服务启动时，不把 DeepSeek 密钥等环境变量传给它（DeepSeek Harness 也是这样做的） |
| 对比公平 | ★ 单 Agent 基线（b1、b2、b5）和多 Agent 拿到**同样的内置工具**，差别仍只在分工；另加消融配置 `full-no-tools`，单独看工具本身带来多少提升 |

## 7. MCP 两个方向的细节

### 7.1 我们当服务端：`firmforge mcp`

- **怎么连**：别的 AI 软件把 `firmforge mcp` 当子进程启动，通过标准输入输出一行一条消息（JSON-RPC 2.0）。设置页给出现成的配置片段，复制进 Claude Code 就能用。
- **提供的 3 个工具**：
  - `list_tasks()`：列出 20 道评测题；
  - `verify_c_module(task_id, files)`：传入源文件，跑判定器第 1–5 层，返回报告（**不跑隐藏测试**）；
  - `kb_search(query)`：查我们的嵌入式知识库。
- **协议版本**：MCP 最新版 2026-07-28 改成"无状态"（不用先握手，每个请求自己带版本号）；但 Claude Code 等现有软件可能还在用 2025-11-25（要先 `initialize` 握手）。★ **两种都支持**；对方说的版本两种都不是时，按规范回"不支持的版本"并列出我们支持的。
- **传进来的文件**：只收 `src/`、`tests/` 下的 `.c`、`.h`，路径不能有 `..`，总共不超过 512 KB；写进临时目录，用完删除。
- **演示价值**：答辩时说明 FirmForge 不只是一个独立软件，还能作为"嵌入式代码质量闸门"嵌进开发者已经在用的 AI 编程工具里（赛题"落地应用"）。

### 7.2 我们当客户端：接入外部 MCP 服务

- 在设置页"添加 MCP 服务"：填名称、启动命令、参数。
- 平台启动它 → 问它有哪些工具 → 登记进工具箱（加 `mcp__` 前缀）。
- 它中途崩了：自动重连，最多 3 次，间隔逐次加长；重连失败就把它的工具从清单里撤掉，并在界面上提示。
- 只支持本机子进程方式（stdio）；★ 远程 HTTP 方式这次不做（要处理登录授权，时间不够）。

## 8. 界面上能看到什么

| 位置 | 内容 |
|---|---|
| 对话 | 每次工具调用一行蓝色记录：谁、调了什么、结果摘要；点开看完整参数和返回 |
| 右下"发给 AI 的内容" | 这次请求带了哪些工具、工具往返的完整记录 |
| 设置 › 工具与 MCP | 内置工具开关、外部服务列表和状态、服务端配置片段和自检按钮 |
| Agent 团队 | 每个 Agent 勾选能用的工具 |
| 电路板 | ★ 芯片上不另外画工具调用，免得太乱 |

## 9. 记录和评测

- 新事件 `tool_called`：Agent、工具名、参数摘要、成功与否、耗时。回放时也能看到。
- `llm_calls/` 保存每次工具往返的完整内容（请求头照旧脱敏）。
- 评测汇总新增两列：平均每题调用工具几次、工具耗时占比。
- `firmforge stats` 按工具统计调用次数、成功率、平均耗时。
- 消融配置 `full-no-tools`：和 full 只差"没有工具"。

## 10. 代码放在哪（核心库，只用标准库）

| 文件 | 做什么 |
|---|---|
| `src/firmforge/tools/registry.py` | 工具箱：登记、按 Agent 过滤、生成发给模型的工具清单 |
| `src/firmforge/tools/builtin.py` | 3 个内置工具 |
| `src/firmforge/tools/runner.py` | 工具调度员：多轮调用循环、次数、超时、截断、回传思考内容、发事件 |
| `src/firmforge/mcp/server.py` | MCP 服务端（`firmforge mcp`） |
| `src/firmforge/mcp/client.py` | MCP 客户端（启动外部服务、发现工具、重连） |
| `src/firmforge/mcp/protocol.py` | 两边共用的消息格式和版本处理 |
| `src/firmforge/llm/fake.py`（改） | 假模型支持"预设的工具调用"，单元测试不联网 |

## 11. 怎么验证（单元测试，全部用假模型，不花钱）

1. 正常调用一次工具后交卷。
2. 连续多轮调用；第 5 轮后不再给工具清单。
3. 工具出错、超时、参数不是合法 JSON：错误信息回给模型，运行不中断。
4. 思考内容被正确回传（检查第二次请求里带着第一次的 `reasoning_content`）。
5. Agent 调用不在自己清单里的工具：拒绝并告诉它。
6. `compile_check` 找不到隐藏测试（防泄露）。
7. MCP 服务端：用子进程分别按 2026-07-28 和 2025-11-25 两种方式走完"列工具 → 调用 → 拿结果"；不支持的版本回正确的错误码。
8. MCP 客户端：接一个测试用的假 MCP 服务（就用我们自己的服务端），能发现工具、调用、断线重连。
9. 评测模式下外部工具确实被关掉。

## 12. 开发顺序

| 顺序 | 内容 | 依赖 |
|---|---|---|
| 1 | 工具箱 + 工具调度员 + 假模型支持工具调用 | 无 |
| 2 | 3 个内置工具 + Agent 定义加 `tools`、`skills`、`memory` 字段 + `firmforge agents` | 1 |
| 3 | MCP 协议公共部分 + 服务端 `firmforge mcp` | 无（可与 1 并行） |
| 4 | MCP 客户端 + 接入 fetch 演示 | 1、3 |
| 5 | 消融配置 `full-no-tools`、统计 | 2 |
| 6 | 用真模型小规模试跑 1–2 道题（由你来跑），看 Agent 是否真的会用工具 | 2 |

界面部分（设置页、对话里的工具记录）等界面草图确认后随桌面软件一起做。

## 13. 需要你拍板的 ★

1. 内置 3 个工具、编码 Agent 全给、测试 Agent 不给 `compile_check`。
2. 单 Agent 基线也给同样的内置工具 + 新增 `full-no-tools` 消融。
3. 一次生成最多 5 轮、结果截 4000 字、超时 60 / 30 秒。
4. 外部 MCP 首批只接 `fetch` 演示，默认关闭、调用前询问、评测时关闭；只做本机 stdio，不做远程 HTTP。
5. MCP 服务端同时支持 2026-07-28 和 2025-11-25 两个版本。
