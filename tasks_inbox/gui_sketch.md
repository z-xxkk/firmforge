## 一、设计方案（按 frontend-design skill 的流程：先定方案 → 对照需求自查 → 做示意图 → 截图自评）

**示意图**：[gui_mockup.png](gui_mockup.png)（静态截图）、[gui_mockup.html](gui_mockup.html)（用浏览器打开的同一张图）。图里的数据是编的，只用来看样子。

### 这个软件给谁用、主要做什么

- **谁看**：答辩评委（看演示视频）和你自己（验收、演示）。
- **主要的事**：一眼看清"一个固件任务被拆成几块、每块走到哪一步、卡在哪一层检查、为什么交给这个 Agent"。
- **题材**：嵌入式固件。这个行业最有辨识度的东西是**电路板**：绿色阻焊层、白色丝印字、金色焊盘、铜走线、芯片封装。

### 核心想法：任务拆分图画成一块电路板

整个界面只在一处用力，就是中间的拆分图，其他地方保持安静、朴素：
- 底色是电路板的阻焊绿，每个模块画成一个**芯片封装**：白色丝印轮廓，左上角有"1 脚标记"。
- 模块之间的依赖画成**走线**（直角加 45° 拐角，和真实布线一样）。上游模块通过后，走线变成金色，表示"这条依赖已经接通"。
- 每个芯片下沿有 **5 个焊盘**，对应 5 层检查（主机编译、交叉编译、资源、静态检查、单元测试）：
  - 还没检查：空心框；
  - 通过：实心金色；
  - 正在检查：橙色闪烁；
  - 失败：红色。
  
  这样不用点开报告，就能直接看出每个模块"走到第几层了"。
- 右上角的小灯表示模块整体状态，旁边一定写文字（等待 / 进行中 / 通过 / 失败），不只靠颜色区分。
- 升级到第几级，用芯片名字旁边的小方框"升级 1–4"表示。

### 配色（5 个基本色 + 状态色）

| 名字 | 色值 | 用在哪 |
|---|---|---|
| 阻焊绿 | #1F4D3A | 拆分图底色、主按钮 |
| 丝印白 | #EEF2EC | 拆分图上的文字和轮廓 |
| 沉金 | #D4AF37 | 焊盘、已接通的走线 |
| 机壳灰 | #E4E7EA / #F6F7F8 | 外框和左右栏 |
| 墨色 | #1D2328 | 正文文字、状态栏 |
| 状态色 | 橙 #FF8A1F 进行中、红 #E5483B 失败、绿 #2FA864 通过 | 状态灯、检查结果 |

### 字体

- **界面文字**用系统自带的中文黑体：Windows 上是微软雅黑，Linux 上是思源黑体 / Noto Sans CJK。不打包中文字体，安装包能小几十 MB。
- **代码里的名字**（模块名、Agent 名、函数原型、报错原文）用等宽字体 JetBrains Mono，开源 OFL 许可证，随软件打包约 300 KB。这些东西本来就是代码，用等宽字体是在说"这是代码"，不是装饰。

### 原则

1. 只有拆分图一处醒目，其他区域用表格和细分隔线，不堆卡片、不加阴影和渐变。
2. 界面文字按使用者的说法写，不按程序内部的叫法：
   - 写"规划完成后等我确认"，不写"human_review"；
   - 写"为什么交给 coder-fast"，不写"score_breakdown"。
3. 唯一自动发生的动画是"进行中"的焊盘和状态灯闪烁，用来提醒"现在在做这里"；其他变化只在事件发生时变一次。
4. 出错时说清楚出了什么事、怎么办，例如"没检测到 Docker：请先启动 Docker Desktop，或者切到'本机'"。

## 二、每一块是做什么的

| 区域 | 显示什么 | 能做什么 |
|---|---|---|
| 工具栏 | 当前后端；工具链是否可用 | 新建运行；打开历史运行目录进入回放；切换 docker / 本机；"检查环境"等于 `firmforge doctor` |
| 左栏：需求与任务 | 20 道评测题（名称 + 难度）；或者自己选需求文档和头文件目录 | 选配置（b1、b2、b3、b4、full、b5、3 个消融配置）；勾选人工确认；b5 才显示 token 预算；开始 / 停止 |
| 中间：拆分图（电路板） | 规划 → 各模块（芯片）→ 集成判定；走线表示依赖。芯片里写：模块名、当前 Agent、第几次尝试（共 6 次）、升级级别、5 个检查层焊盘 | 单击模块：右栏显示它的调度得分和尝试记录；双击：下方切到该模块最近一次的判定报告；可以滚轮缩放、拖动 |
| 右上：Agent 状态 | 每个 Agent 的档位（快 / 强）、正在做什么、累计调用次数、token、费用 | 只看 |
| 右栏中部："为什么交给它" | 选中模块被分配时每个候选 Agent 的成功率、成本、负载、探索、总分，以及选中原因（就是 `node_assigned` 事件里的数据） | 只看 |
| 右栏下部：尝试记录 | 选中模块每次尝试的结果和诊断要点 | 点一行，下方切到那次的检查结果 |
| 下方：事件日志 | 每个事件一行，文字和命令行实时输出一致 | 可按模块筛选 |
| 下方：判定报告 | 每层一个色块：主机编译、交叉编译、资源、静态检查、单元测试、隐藏测试（只有评测才有），通过绿、失败红、跳过灰 | 点色块展开该层的详细输出 |
| 下方：交付物 | 结束后显示 `final/report.md`，列出交付的文件 | "打开所在文件夹" |
| 状态栏 | 运行编号、用时、总 token、费用、结论 | 只看 |

## 三、交互流程

**1. 实时运行（docker 后端，默认）**
1. 选题、选配置，点"开始运行"。
2. 软件在后台执行 `docker run … firmforge run --task … --config …`，运行目录挂载到本机的 `.ff_runs/`。
3. 软件每 0.2 秒读一次新增的 `events.jsonl` 行，节点按事件变色（★ 0.2 秒）。
4. 结束后状态栏显示结论，"交付物"页显示报告。
5. 点"停止"：结束容器，结论记为"不完整"。

**2. 实时运行（local 后端）**：在后台线程里直接调用核心库的 `run()`，事件直接送进界面，其他与 docker 相同。需要本机装好工具链，没装时"检查环境"会列出缺什么。

**3. 回放**
1. 点"打开历史运行"，选一个 `.ff_runs/<运行编号>/` 目录。
2. 界面清空，按事件的时间间隔重放，默认 4 倍速（★）。
3. 可以暂停、从头开始、拖进度条、换速度。
4. 回放和实时运行走同一套显示代码，只是事件来源不同（ARCHITECTURE §2.8）。回放时左栏变灰不能操作。

**4. 人工确认规划（勾选"人工确认"时）**

规划完成后弹窗，运行暂停：

```
┌─ 确认规划（第 1 / 3 次）──────────────────────────────┐
│ 模块 1  crc   CRC-16/MODBUS 计算                       │
│         文件：src/crc16.c、src/crc16.h                 │
│         接口：uint16_t modbus_crc16(...)               │
│ 模块 2  pdu   功能码 03/06 处理      依赖：crc         │
│ 模块 3  rtu   RTU 帧收发             依赖：crc、pdu    │
│                                                        │
│ 修改意见（不填 = 确认）：                              │
│ ┌────────────────────────────────────────────────────┐ │
│ │                                                    │ │
│ └────────────────────────────────────────────────────┘ │
│                         [让规划重做]   [确认，继续]     │
└────────────────────────────────────────────────────────┘
```
第 3 次仍不确认，结论为 rejected（DECISIONS 第 46 条）。

**5. 升级到第 4 级（转人工）**：同样弹窗，列出这个模块的失败要点，下面一个输入框写给编码 Agent 的提示；"提交提示"让它再改一次，"放弃"记为失败（第 52 条）。

## 四、★ 小细节

1. DAG 图自动排布：按依赖深度从上到下分层，同层从左到右按规划顺序；不引入画图库。
2. 节点状态：右上角状态灯 + 文字（等待、进行中、通过、失败、跳过）；等待和跳过的芯片轮廓画虚线、整体变淡；进行中的芯片外面多一圈橙色虚线框。
3. 窗口最小 1280 × 800，三栏之间可以拖动调宽度。
4. 界面文字全部中文。外框跟随系统的浅色 / 深色主题；中间的电路板两种主题下都是绿色。
5. 电脑上没装 Docker 时，docker 选项变灰并提示"没检测到 Docker"，自动切到 local。
6. 开始运行前检查 `.env` 里有没有 API key（只检查有没有，不显示内容）；没有就提示，不启动。
7. 界面只读事件和运行目录，不直接访问引擎内部（CLAUDE.md 核心与界面分离）。
8. 不做"批量评测"页：评测继续用命令行，桌面软件只管单次运行和回放（交付物清单里没有这项，阶段 4 之后功能冻结）。

## 五、需要你选的一件事

**docker 后端下，人工确认的结果怎么交还给容器里的程序？**

| 方案 | 怎么做 | 好处 | 坏处 |
|---|---|---|---|
| A（推荐）通过标准输入 | 启动容器时保持输入通道打开；收到 `human_wait` 事件后弹窗，把你的回答当作"在终端里打字"送进去 | 核心代码不用改，命令行已有的人工确认直接复用 | 依赖命令行的提问顺序，以后改提问方式要两边一起改 |
| B 通过应答文件 | 核心等待运行目录里出现一个应答文件，界面把回答写进这个文件 | 界面和命令行完全解耦 | 核心要加一套"等文件"的逻辑和测试，多一个出错点 |
