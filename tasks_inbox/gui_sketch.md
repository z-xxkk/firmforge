## 一、整体结构

最左边一条竖栏，用来切换 4 个工作区：

| 工作区 | 做什么 |
|---|---|
| **对话**（打开软件默认进这里） | 用一句话提需求 → 需求 Agent 追问、整理需求 → 规划 Agent 拆模块、你确认 → 看 Agent 团队边聊边干 → 结束后追问结果 |
| **工作流** | 可视化设计器：画流程、改参数、检查、存成新版本、试运行 |
| **Agent 团队** | 每个 Agent 的角色、版本、模型档位、技能、能用的工具、用不用记忆，以及历史表现（成功率、平均花费）；可以注册新 Agent、切换版本 |
| **历史回放** | 运行记录列表；打开任意一次，按倍速重放对话和电路板 |

## 二、对话工作区（[gui_chat.png](gui_chat.png)）

```
┌──┬────────────────────────┬──────────────────────────────────────────┐
│对│ 标题、配置、后端  [停止] │                                          │
│话│────────────────────────│        电路板：模块 = 芯片，依赖 = 走线    │
│  │ 你：帮我写一个 Modbus…  │        每个芯片 5 个焊盘 = 5 层检查        │
│工│ analyst：先确认两件事…  │                                          │
│作│ planner：拆成 3 个模块  │                                          │
│流│   [确认，开始写][提意见] │──────────────────────────────────────────│
│  │ ▬▬▬▬▬ crc 全部通过      │ [检查结果] [代码] [为什么交给它] [团队]   │
│团│ ▬▬▬▬▬ pdu 单元测试没过  │  点对话里的消息或者电路板上的芯片，       │
│队│ diagnoser：问题在 57 行 │  这里显示对应的详细内容                   │
│  │ ● coder-fast 正在改…   │                                          │
│  │ [输入框]         [发送] │                                          │
└──┴────────────────────────┴──────────────────────────────────────────┘
 状态栏：运行编号、用时、token、费用、结论
```

**对话里会出现什么**

| 谁说话 | 什么时候 | 内容 |
|---|---|---|
| 你 | 开始前、需要你确认时、结束后 | 需求、回答追问、确认或修改意见、追问结果 |
| analyst（需求分析，**新增的 Agent**） | 开始前；结束后 | 追问不清楚的地方，整理出需求文档和公共头文件，你点"开始运行"；结束后回答你的追问 |
| planner（规划） | 规划完成 | 模块列表 + "确认，开始写""提修改意见"两个按钮（就是原来的人工确认弹窗，搬进对话里） |
| coder、tester | 交卷时 | "写好了"，附文件名，点开在右下看代码 |
| 检查 | 每次检查完 | 一行：5 格小条（和芯片焊盘同一套颜色）+ 结论 |
| diagnoser（诊断） | 每次没通过 | 问题在哪、交给谁改 |
| 升级、回滚 | 发生时 | 一行灰字说明 |
| 转人工（升级第 4 级） | 发生时 | 列出失败要点，输入框变成"给编码 Agent 的提示" |

对话和电路板是**同一份事件**的两种画法：对话按时间讲经过，电路板看全局状态。点对话里的消息，电路板上对应的芯片会高亮，反过来也一样。

★ 选评测题也在对话工作区：输入框上方有"选一道评测题"，选了就跳过需求对话，直接用题目的需求文档开始。

## 三、工作流设计器（[gui_designer.png](gui_designer.png)）

### 我对"可视化的工作流设计器"的理解

赛题背景里批评现有方案"多为脚本化或硬编码的 Agent 流水线，**缺乏可视化的工作流设计器、动态条件分支、循环控制与异常回退机制**"。所以设计器要证明的是：**流程不是写死在代码里的，用户能看到、能改，改完平台照着新流程跑。** 参考 Dify 的工作流编辑器（画布、单节点调试、发布版本）和 LangGraph Studio（图形化展示、运行时打断和人工介入），它应该做到 7 件事：

| # | 功能 | 说明 |
|---|---|---|
| 1 | 画流程 | 从左边拖步骤到画布、连线、删除；8 种步骤：Agent 干活、检查、并行、条件、循环、子流程、每个模块各跑一遍、等人确认（就是现在引擎支持的 7 类节点，"子流程"和"每个模块各跑一遍"分开列） |
| 2 | 子流程嵌套 | 子流程画成"层次图框"，可以展开在旁边，也可以双击进去单独编辑 |
| 3 | 改每一步的设置 | 右栏：Agent 步骤选角色或指定某个 Agent；循环设上限和停止条件；条件选判断依据；等人确认可以设"只在勾选人工确认时出现" |
| 4 | 保存前检查 | 没连上的步骤、没有上限的循环、角色没有注册 Agent、引用不存在的子流程、引擎不支持的组合，都标在图上，不让保存 |
| 5 | 图和文件是同一份 | 保存就是写 `workflows/*.toml`；手改 TOML 再打开，图也跟着变。"查看 TOML"按钮并排显示文字版。赛题说"可视化或代码化"，我们两种都有，而且是同一份 |
| 6 | 版本 | 每次保存成新版本号，旧版本保留；运行时选用哪个版本，运行记录里写明 |
| 7 | 试运行 | 选一道题直接用当前版本跑，跳到对话工作区；运行时电路板旁边可以切换成"流程视图"，在这张图上看到正走到哪一步 |

图纸风格用**原理图**：浅色网格纸、蓝色连线、右下角有"标题栏"写着工作流名称、版本、修改日期（真实电路原理图都有这个框）。**设计流程用原理图，运行结果用电路板**，和硬件工程师"先画原理图、再做板子"是同一个顺序。

### 诚实的边界

设计器只能画引擎**真的能执行**的东西，否则就是夸大。现在引擎有这些限制：
- 主流程只认"规划 → 等人确认 → 每个模块 → 集成检查"这几种步骤；
- 循环的内容只有"修正一轮"一种；
- 子流程里不能放"等人确认"。

示意图里新加的"accept 等人验收"就是现在还跑不了的例子，要么放宽引擎，要么设计器不让放（见第六节第 2 问）。

## 六、其余交互（沿用第 1 版）

- 后端：docker（默认）或本机；没装 Docker 时 docker 选项变灰并说明怎么办。
- 回放：历史回放工作区打开一次运行，默认 4 倍速，可暂停、拖进度条；对话和电路板一起重放。演示视频用这个模式录。
- 停止运行：结论记为"不完整"。
- 开始前检查 `.env` 里有没有 API key（只看有没有，不显示内容）。
- 界面只读事件和运行目录，不直接访问引擎内部。
- 不做"批量评测"页，评测用命令行。

## 七、需要你选的 3 件事

**1. 对话框能做到哪一步？**

| 方案 | 能做什么 | 代价 |
|---|---|---|
| A 只看和确认 | 对话框显示 Agent 们的进展；只在需要你确认时能回复 | 最小，不用新 Agent |
| **B（推荐）A + 需求对话 + 结束后追问** | 开始前和需求 Agent 聊，它追问并整理出需求文档和头文件；结束后可以问"为什么 pdu 失败了""改成支持功能码 16"（后者开一次新运行） | 新增 analyst Agent；补上赛题"需求理解"这一环。自己写的需求没有隐藏测试，报告里会写明"只经过 Agent 自己写的测试" |
| C B + 运行中随时插话 | 运行中打的字会交给下一个干活的 Agent | 引擎要改；评测结果会受人影响，评测模式必须关掉 |

**2. 设计器能画到什么程度？**

| 方案 | 说明 |
|---|---|
| A 只能画引擎现在支持的 | 工作量小；能改的东西少（基本只能开关审查、人工确认、改循环上限） |
| **B（推荐）放宽引擎几处再做设计器** | 允许：任何位置放"等人确认"；Agent 步骤指定具体 Agent（不只是角色）；条件可以走"否"分支；子流程里可以再嵌子流程。设计器能画的都能跑，并且每种组合都有单元测试 |
| C 完全自由的流程 | 等于重写引擎，时间不够 |

**3. docker 后端下，你在界面上的回复怎么交给容器里的程序**（第 1 版遗留，推荐 A：通过标准输入，核心不用改）。
