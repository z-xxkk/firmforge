## 1. 背景与约束

- **比赛**：第五届"未来杯"技术大赛，赛题一"Agent 编排创新应用"。要求做一个有创新的多 Agent 编排应用。
- **团队**：1 名项目负责人（学生，负责想法、决策、验收，不写代码）+ AI 编程助手（写全部代码和测试）。
- **时间**：今天 2026-11-10。11/11 晚功能冻结；11/12 跑最后一轮正式评测；11/20 前交方案书（≥5000 字）、PPT、演示视频。**剩余约 9 天，其中可改功能的只有 1 天。**
- **预算**：评测用真实模型要花钱，单轮评测上限约 15 元人民币。
- **技术栈**：Python ≥3.11，核心库只用标准库（自己用 urllib 实现 OpenAI 兼容接口）；大模型 DeepSeek（deepseek-flash / 更强档）；桌面软件 PySide6；只支持 Linux。
- **硬件**：ESP32-C3 SuperMini 开发板（ESP-IDF v6.1），面包板接 MPU6050（实为 MPU-6500 兼容仿制芯片）和 MAX30102 传感器。

## 2. 项目是什么（一句话）

一个**面向嵌入式固件开发的多 Agent 编排与验证平台**：用户给一段嵌入式 C 模块需求，平台调度多个 LLM Agent 分工写代码和测试，用**客观判定器**（编译器、合规检查、单元测试、**真板子上跑的测试**）逐层检查，失败就进入修正循环，最后交付通过检查的代码和验证报告。

核心主张（项目自己设定的论点）：
1. LLM 写固件最大的问题是**硬件事实写错**（寄存器位、引脚限制、API 版本），而且模型自己看不出来；
2. 所以要用**有出处、经过核对、人工确认过的规则库**约束 Agent，并用**真板子**判定，而不是让 LLM 评 LLM。

## 3. 已实现并测试过的功能

### 3.1 两条流程
- **旧流程（纯逻辑模块，宿主机测试）**：规划 Agent 拆模块（DAG，可并行）→ 编码 / 测试 / 审查 / 诊断 Agent → 判定器 5 层（编译、资源预算、cppcheck 静态分析、单元测试 + gcov 覆盖率、隐藏测试）。20 道评测题（数据结构、协议、状态机、驱动），每题带参考答案和"变异体"自检。
- **嵌入式新流程（上板）**：需求 → 查资料 Agent 从芯片手册 PDF 提炼规则 → 规则判定器核对 → 人工确认入库 → 设计 Agent 分层（硬件层 / 逻辑层）→ 编码 Agent + 测试 Agent → 合规检查 → ESP-IDF 编译 → **烧录到真板跑 Unity 测试** → 诊断 Agent 判断是代码、测试、规则还是硬件的问题 → 分派修正。

### 3.2 Agent 角色（agents/*.toml，每个有档位、思考强度、技能、工具、版本）
analyst（对话分析）、planner（规划）、designer（嵌入式分层设计）、coder-fast / coder-strong（编码）、tester（写测试）、reviewer（审查）、diagnoser（诊断失败归因）、researcher（查手册提炼规则）、rule_checker（核对规则是否忠于原文）。
- 编排：DAG 并行、按"成功率、成本、负载、探索"打分调度（smart 调度）、修正循环、回滚、人工节点、工作流用 TOML 描述，可在图形设计器里拖拽编辑。
- Agent 之间通过结构化任务单和"文件块"输出协议交互；**Agent 不能直接操作文件系统或命令行**（与 Claude Code / Cursor 这类通用编程 Agent 不同），只能交文件，由平台写入、编译、运行。

### 3.3 规则库机制（项目自认为最有特色的部分）
- 每条规则有：适用范围、一句话内容、**出处（资料编号、页码、原文引用）**、来源等级（官方手册 / 官方代码 / 镜像 / 实测 / 用户）、机器检查项（如"禁止调用某 API""禁止用某 GPIO""A 必须在 B 之前调用"）。
- 规则判定器：格式检查 → **原文核对**（引用必须在 PDF 对应页里逐字找得到）→ 接口类规则用对应版本 ESP-IDF 头文件编译核对 → 语义核对 Agent 判断规则是否忠于原文 → 人工逐条通过或驳回。
- 读 PDF：另存按版面排列的文字；按 PDF 坐标算出寄存器表里每个单个位在第几位（"寄存器位标注"），明确标注"平台算出、不是原文"。
- **实测纠正**：上板实测发现两处资料与硬件不符——MPU 模块 WHO_AM_I 是 0x70（仿制 MPU-6500，不是手册说的 0x68）；MAX30102 手册说 TEMP_EN 自动清零即完成，实测清零 0.26 ms 但数据 27.5 ms 才出来。实测记录登记为资料，规则可引用，评测汇总自动披露。
- 当前正式规则库：47 条，负责人逐条确认。

### 3.4 评测设计
- **上板评测**：11 道上板题（外设 5、驱动 5、综合 1），每题有公共头文件（锁定接口）、参考答案、**隐藏测试**（任何 Agent 都看不到，53 个上板用例）、34 个故意写错的变异体（自检时全部被抓住）。
- **四种配置，每级只多一样东西**：single（单 Agent，只看编译错误）→ none（多 Agent + 自己写测试上板 + 诊断，不给规则）→ unverified（再加当场提炼、未核对的规则）→ verified（改用核对并人工确认的规则库）。所有配置用同一个判定：固定合规规则 → 编译 → 上板隐藏测试。
- 每个用例单独开机运行，用例前软复位外接传感器，避免状态污染。

### 3.5 其他
- 命令行全套命令；运行记录可回放；花费实时统计和上限；MCP 服务端；经验库（SQLite）；性能测试。
- 桌面软件 6 页：对话（发起运行、看每个模块每次尝试的检查结果、上板测试用例与串口原文、导出代码）、硬件（档案、规则库、在界面上确认规则）、评测（设置、预估花费、结果表、暂停续跑）、工作流设计器、Agent 团队、设置。
- 测试：414 个单元测试（全部用假模型，不联网），随机操作"猴子"测试、故障注入、变异测试（判定代码杀死率 84%）。

## 4. 实测数据（如实）

### 4.1 旧流程正式评测（10 题 × 1 次）
| 配置 | 最终通过 | 首次通过 | 每通过一题成本 |
|---|---|---|---|
| b2 单 Agent + 修正 | 10/10 | 8/10 | 0.35 元 |
| full 多 Agent | 10/10 | 9/10 | 0.48 元 |
| b5 同等花费从头重写 | 9/10 | 6/10 | 0.75 元 |

结论：题目对模型偏简单（天花板），**不能说明多 Agent 比单 Agent 强**；只能说明"带报错修改"优于"从头重写"。

### 4.2 上板评测第 1 轮（6 题 × 4 配置 × 2 次 = 48 次，11.26 元）
| 配置 | 通过 |
|---|---|
| single | 5/12 |
| none | 7/12 |
| unverified | 7/12 |
| **verified（可信规则库）** | **4/12（最低）** |

差异不显著（p≈0.41）。**这一轮不支持"可信规则库提高通过率"。** 失败分析：一条规则只写了"等完成标志"、没写在第几位；外接传感器不随芯片复位（已修评测设计）。

### 4.3 失败分析案例（单列，不并入正式数据）
max30102_temp 题：verified 两次都把 DIE_TEMP_RDY 写在错的位上。根因链：规则库缺这条 → 平台读 PDF 时丢了表格列位置 → 模型靠数空格对列不可靠。平台加了"按坐标标注寄存器位"后，规则写对了第 1 位，案例 1/2 通过（另一次错在温度小数换算）。

### 4.4 待跑
11/12 正式评测：6 题 × 4 配置 × 2 次，上限 15 元。结果无论偏向哪种配置都如实写。

## 5. 已知的弱点和没做的（如实）

- **核心论点目前没有数据支撑**：verified 在第 1 轮最低；样本小（每格 2 次），即使正式轮也很难得到显著结论。
- Agent 不能自主操作文件 / 命令行，只能在平台规定的流程里交文件；和通用编程 Agent（Claude Code、Cursor、Devin）比，自主性弱。
- 只支持一块板子、一套固定接线、11 道题；换板需要人写硬件档案。
- 界面还没有用真实模型从头到尾跑过（只用假模型 + 真板验证过）。
- 最近一周大量时间花在桌面软件、图形工作流设计器交互、找 bug 上。负责人感觉"项目越做越像普通的 Agent 平台，而且是半成品"，说不清缺什么。
- 编排部分（DAG、调度、工作流设计器）和 Dify、Coze、LangGraph、n8n 等现成产品相比没有优势。

## 6. 相关工作（项目调研过的）
- EmbedAgent 等论文：LLM 在嵌入式任务上表现差，迁移到 ESP-IDF 最好约 29%，写明版本仍会用错函数；
- 通用编程 Agent（Claude Code 等）：能操作文件和命令行，但没有硬件在环判定，也不管硬件事实的出处。
