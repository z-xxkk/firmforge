# 桌面软件接入嵌入式新流程：界面草图（第 1 版，待负责人确认）

起草：Claude Code，2026-11-09。沿用第 4 版界面的视觉风格（浅色简约、松石绿是唯一强调色、圆角分档、每道缝都能拖），不另起一套。**确认后才开始写代码。**

## 为什么要做

现在桌面软件只能跑旧的纯逻辑题。新流程（硬件档案 → 规则 → 设计 → 编码、测试 → 上板 → 诊断修正）和上板评测只能在终端里跑；规则确认也只能在终端里逐条打字，之前在终端里确认时出过好几次差错。赛题要求视频展示"平台界面、编排过程、调度执行、结果验证与反馈循环"，这些都要在界面上看得到。

## 一、对话页：跑新流程（[gui_board_run.png](gui_board_run.png)）

布局不变：会话列表、对话、右上模块图、右下详情。改动：

| 改动 | 借鉴自 |
|---|---|
| 对话标题旁标出"上板""规则库"，表示这次跑的是新流程、用哪种规则 | ★ |
| 规则这一步在对话里显示成一条消息：用了哪些范围的规则、各多少条、有几条来自实测 | ★ |
| 模块卡片标明"硬件层，上板"或"逻辑层，电脑上测"；进度条从旧的 5 段改成 3 段：编译、合规、测试 | GitHub Actions 运行图：每个任务一个状态图标，图随运行实时更新（[文档](https://docs.github.com/en/actions/how-tos/monitor-workflows/use-the-visualization-graph)） |
| 详情区新增"上板测试"标签：每个用例一行，**没通过的自动展开**显示失败原因和代码位置；下面是串口输出原文，失败行标红 | GitHub Actions 日志："失败的步骤自动展开显示结果"（[文档](https://docs.github.com/en/enterprise-server@3.16/actions/how-tos/monitor-workflows/use-workflow-run-logs)）。PlatformIO 的教训：它在 VS Code 的测试结果面板直接贴 Unity 原始输出，用户反映看不到测试输出、换行丢失（[社区帖](https://community.platformio.org/t/challenges-using-vs-code-testing-explorer/42044)），所以这里先解析成用例列表，原文放在下面备查 |
| 详情区新增"用到的规则"标签：这次运行用到的规则和出处 | ★ |
| 底部状态栏常驻：板子型号、串口、是否连着；ESP-IDF 版本；规则库条数；本次用时、token、费用。点板子那一项可以换串口 | ESP-IDF 的 VS Code 插件把串口和芯片型号放在状态栏，点一下就能换（[官方文档](https://docs.espressif.com/projects/vscode-esp-idf-extension/en/latest/flashdevice.html)） |
| 工具调用一行显示读了哪份手册第几页，以及找到的位标注 | ★ |

诊断、修改、再上板的循环，按原样在对话里一条条出现，这就是视频要展示的"反馈循环"。

## 二、硬件页：档案和规则库（[gui_hardware.png](gui_hardware.png)）

三栏：硬件档案、规则库列表、规则详情。

| 改动 | 借鉴自 |
|---|---|
| 档案里每个值后面标来源：你填的、资料、实测、默认（这正是档案文件里本来就记录的） | ★ |
| 档案里列出实测记录 M-001 到 M-004，说明规则可以引用它们 | ★ |
| 规则库列表按范围分组，顶部按状态筛选：等你确认、已确认、退回 | ★ |
| 列表顶部可以发起"查资料提炼规则"：选范围，显示预计花费，再点开始 | ★（花费预估沿用 board-eval 的 `--plan`） |
| 规则详情：规则原文、出处（资料、页码、等级）、引用的原文高亮、这一页的位标注（虚线框，写明"不是原文"）、7 步核对每一步的结果 | ★ |
| **在界面上确认规则**：驳回时写一句理由，或点"通过"；可以只确认一部分，下次接着来 | GitHub 拉取请求的审查：写一段意见，再选"批准"或"要求修改"后提交（[文档](https://docs.github.com/en/enterprise-server@3.16/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request)） |
| 规则的出处只能证明一部分时，在详情里提示一句，例如"引用的原文只说默认全部关闭，bit1 来自位标注" | ★（来自 DIE_TEMP_RDY 案例发现的问题） |

## 三、评测页（[gui_eval.png](gui_eval.png)）

三栏：设置、结果、运行记录。

| 改动 | 借鉴自 |
|---|---|
| 左栏选题目、配置（每种配置用一句话说明多了什么）、每格跑几次、花费上限；下面先算好"共多少次、按上一轮估计约多少钱、多久、verified 缺不缺规则"，再点开始 | 沿用 `board-eval --plan`（DECISIONS 第 92–94 条） |
| 结果是题目 × 配置的表，每次运行一个小方块：绿通过、红没通过、琥珀正在跑；点方块打开那次运行的完整过程（在对话页回放） | GitHub Actions 运行图：点一个任务打开它的日志 |
| 下面是"没通过的卡在哪一层"和隐藏用例通过率，和 summary.md 一致 | 沿用 summary.md |
| 右栏是运行记录，和终端里一行一次的输出相同 | ★ |
| 中断后再点开始，接着没跑完的继续 | 沿用 board-eval 的断点续跑 |
| 页面底部写明：来自实测的规则会单独列出，隐藏测试只给评测用 | DECISIONS 第 95 条 |

## 五、需要你选的

1. **做到哪一步**：
   - A（推荐）三页都做，按"对话页上板运行 → 硬件页 → 评测页"的顺序，先做视频最需要的；
   - B 只做对话页和硬件页，评测仍在终端跑，界面只显示已有结果；
   - C 只做对话页。
2. **上板时用哪种后端**：Docker Desktop 在 Windows 上不能直接把 USB 板子交给容器。
   - A（推荐）凡是要上板的运行一律用本机后端；docker 后端只跑不上板的旧流程；
   - B Linux 下给容器透传串口（`--device`），Windows 只能用本机后端。
3. **规则确认放到界面上**（终端里的确认照旧保留）：是否同意。
