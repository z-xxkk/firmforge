## 题 11：XMODEM 接收端 xmodem_rx（协议，难度 3）

### 参照了什么

Chuck Forsberg 编《XMODEM/YMODEM Protocol Reference》[1]，其中收录了 XMODEM 原作者 Ward Christensen 的协议说明（1982）和 John Byrns 的 CRC 扩展说明（1985）。核对过的原文要点：

| 内容 | 原文要点 | 出处 |
|---|---|---|
| 控制字符 | SOH 01h、STX 02h、EOT 04h、ACK 06h、NAK 15h、CAN 18h、C 43h | 6.1 节 |
| 128 字节块 | SOH、块号、255 − 块号、128 字节数据、校验 | 6.2 节图 7 |
| 1024 字节块 | 用 STX 代替 SOH，数据 1024 字节；接收方要能接受两种块混着来；块号照常加 1 | 3.3 节 |
| 块号 | 从 1 开始，每块加 1，FFh 之后回到 **00h**（不是 01h） | 6.2 节 |
| 校验和模式 | 只对数据字节求和，丢掉进位（1 字节） | 6.2 节 |
| CRC 模式 | 2 字节，**高字节在前**；生成多项式 X^16 + X^12 + X^5 + 1 | 7 节图 9、7.1 节 |
| 进入 CRC 模式 | 接收方用 C 代替第一个 NAK；发送方不支持就不理会。接收方可以重发几次 C，但不能太多次，然后改发 NAK、切到校验和模式；原文示例是发 4 次 C 后改发 NAK | 7.2 节、图 11 |
| 重复块 | 收到上一块的重复（发送方没收到 ACK 而重发）：正常，**回 ACK、丢掉数据** | 6.3.2 节 |
| 失步 | 块号既不是期望的、也不是上一块：致命错误，**发 CAN 中止** | 6.3.2 节 |
| 出错重试 | 所有错误重试 10 次 | 6.3.1 节 |
| 取消 | 连续两个 CAN 才算对方取消（单个 CAN 可能是线路干扰） | 3.1 节 |
| 结束 | 发送方发 EOT，收到 ACK 才算结束；示例里接收方收到 EOT 回 ACK | 6.3.3 节、图 11/12 |
| 最后一块 | 不会有"短块"，不足的部分由发送方填充 | 6.2 节 |

### 怎么用

★ **做成事件驱动，不自己等待、不自己计时**：调用方每收到一个字节就交给模块，超时由调用方计时后通知模块（原文：等块开始 10 秒、块内每字节 1 秒、握手阶段 3 秒）。模块每次告诉调用方"该回什么"。理由：题目没有延时函数，裸机上通常也是在串口中断里一字节一字节喂进来。

模块提供：开始接收（返回第一个要发的字符）、喂一个字节、通知超时、查询状态和已收字节数。接收的数据写进调用方提供的缓冲区。

### 规则

| 情况 | 应该怎样 | 依据 |
|---|---|---|
| 开始 | 回 C（请求 CRC 模式） | [1] 7.2 节 |
| ★ 握手时超时 | 共发 4 次 C；第 4 次之后再超时就改回 NAK，进入校验和模式 | [1] 图 11 的示例次数 |
| 收到 SOH / STX | 开始收一块：之后是块号、反码、128 / 1024 字节数据、校验（CRC 模式 2 字节高位在前，校验和模式 1 字节） | [1] 3.3、6.2、7 节 |
| 块号和反码对不上、校验错 | 回 NAK，错误次数加 1 | [1] 6.3.2 节 |
| 块号是期望的 | 数据存进缓冲区，回 ACK，错误次数清零 | [1] |
| 块号是上一块的 | 回 ACK，丢掉数据 | [1] 6.3.2 节 |
| ★ 还没收到任何块时来了块号 0 | 当作失步处理（XMODEM 没有第 0 块） | 我的选择 |
| 块号是别的 | 中止：回 CAN，状态为"失步" | [1] 6.3.2 节 |
| 块内超时（字节没收齐） | 丢掉这一块，回 NAK，错误次数加 1 | [1] 6.3.2 节 |
| 等块时超时 | 回 NAK（握手阶段按上面的 C 规则），错误次数加 1 | [1] 6.3.2 节 |
| 连续错误达到 10 次 | 中止：回 CAN，状态为"错误太多" | [1] 6.3.1 节 |
| 等块时收到连续两个 CAN | 状态为"对方取消"，不回复 | [1] 3.1 节 |
| ★ 只收到一个 CAN，下一个字节不是 CAN | 当作干扰，忽略那个 CAN，照常处理下一个字节 | 原文"两个 CAN 才算"的推论 |
| ★ 等块时收到其他字节（不是 SOH/STX/EOT/CAN） | 忽略，等超时再 NAK | 原文要求 NAK 前先等线路安静 |
| 收到 EOT | 回 ACK，状态为"完成" | [1] 图 11、图 12 |
| ★ 缓冲区放不下新的一块 | 中止：回 CAN，状态为"缓冲区不够" | 我的选择 |
| ★ 中止时回的 CAN | 模块回复"取消"，由调用方连发 2 个 CAN | 对方也要两个 CAN 才认 |
| ★ 已收字节数 | 按整块计（包含发送方的填充字节），不去掉填充 | 原文：协议本身不知道真实文件长度 |
| 1024 与 128 字节块混着来 | 都接受 | [1] 3.3 节 |

**判卷方式**：隐藏测试模拟发送方，按原文的几个数据流示例（图 8、图 11、图 12）逐字节喂进去，检查每一步的回复；另测线路干扰（校验错、反码错、块内超时）、重复块、失步、连续两个 CAN、10 次出错上限、块号 FFh → 00h 回绕、缓冲区不够。

**错卷（计划）**：块号回绕到 01h；CRC 低字节在前；重复块回 NAK（发送方会一直重发）；一个 CAN 就当取消。

## 题 12：MAVLink 解析器 mavlink_parser（协议，难度 3）

### 参照了什么

MAVLink 官方文档《Packet Serialization》[2] 和官方 C 参考实现 [3]（`checksum.h` 里的 CRC 算法、`minimal.xml` 里的 HEARTBEAT 定义）。核对过的原文要点：

| 内容 | 原文要点 | 出处 |
|---|---|---|
| v1 帧 | FEh、长度、序号、系统号、组件号、消息号（1 字节）、负载、校验 2 字节；共 8–263 字节 | [2] |
| v2 帧 | FDh、长度、不兼容标志、兼容标志、序号、系统号、组件号、消息号（3 字节，低位在前）、负载、校验 2 字节、可选 13 字节签名；共 12–280 字节 | [2] |
| 校验范围 | 除起始字节和签名以外的全部字节，**再加上该消息的 CRC_EXTRA 一个字节**（只参与计算，不在线上传） | [2] |
| 校验算法 | CRC-16/MCRF4XX，初值 FFFFh；校验值**低字节在前** | [2]、[3] |
| 核对 | 按参考实现的算法，"123456789" 的结果是 6F91h（与公开的 MCRF4XX 校验值一致）；HEARTBEAT 的 CRC_EXTRA 算出来是 50，负载 9 字节 | 自己计算 |
| 不认识的不兼容标志 | 必须丢弃 | [2] |
| 签名 | 不兼容标志 01h 表示带签名，帧尾多 13 字节 | [2] |
| v2 负载截断 | 发送方去掉负载末尾的 0；接收方要按完整长度补 0 后使用；第一个字节不截 | [2] |
| v1 长度 | 每种消息固定 | [2] |
| 起始字节不对 | 跳过 | [2] |

### 怎么用

调用方提供一张"消息表"：每种消息的消息号、完整负载长度、CRC_EXTRA（真实系统里由代码生成器产出）。解析器每次喂一个字节，收到完整的一帧时报告结果，并把这一帧的信息（版本、序号、系统号、组件号、消息号、补齐后的负载、是否带签名）交给调用方。

### 规则

| 情况 | 应该怎样 | 依据 |
|---|---|---|
| 等帧头时收到 FEh / FDh 以外的字节 | 跳过 | [2] |
| 校验 | 按上表计算，与帧里的值比较（低字节在前） | [2]、[3] |
| 校验对 | 报告"收到消息" | [2] |
| 校验错 | 报告"校验错"，丢弃，坏帧计数加 1 | [2] |
| ★ 消息号不在消息表里 | 报告"未知消息"并丢弃（不知道 CRC_EXTRA 就无法验证） | 我的选择；C 库的默认做法也是无法验证 |
| ★ v1 长度与消息表不同 | 报告"长度不对"并丢弃 | [2]：v1 长度固定 |
| v2 长度比消息表短 | 接受，负载末尾补 0 到完整长度 | [2] |
| ★ v2 长度比消息表长 | 报告"长度不对"并丢弃 | 我的选择：消息表里写的是含扩展字段的完整长度 |
| ★ v2 长度为 0 | 报告"长度不对"（原文规定第一个字节不截，负载至少 1 字节） | [2] 的推论 |
| v2 不兼容标志含 01h 以外的位 | 丢弃，报告"不支持的标志" | [2] |
| v2 带签名（01h） | 读完 13 字节签名，标记"带签名" | [2] |
| ★ 签名内容 | 不验证（验证要密钥和时间戳，超出本题），只跳过 | 我的选择 |
| ★ 坏帧之后 | 从坏帧起始字节的**下一个字节**开始重新找帧头（坏帧里可能藏着真正的帧头） | 与串口收包题第 29 条一致 |
| ★ 丢包统计 | 同一系统号 + 组件号的序号不连续时，按差值累计丢包数（序号 255 之后是 0）；最多记 8 个来源，超过的不统计 | 我的选择 |

**判卷方式**：隐藏测试用自己的生成器按参考算法造帧：真实的 HEARTBEAT（v1 和 v2）、截断负载、签名帧、坏校验、未知消息、错误标志、帧头之前的垃圾字节、坏帧里藏着帧头、序号回绕、多来源丢包。

**错卷（计划）**：校验时漏掉 CRC_EXTRA；校验值高字节在前；v2 截断负载不补 0；坏帧后跳过整个坏帧（藏在里面的真帧丢失）。

## 题 13：1-Wire 温度传感器 onewire_ds18b20（驱动，难度 3，多模块）

### 参照了什么

Maxim 应用笔记 **AN187《1-Wire Search Algorithm》（2002-03-28）**[4] 和 **DS18B20 数据手册** [5]。核对过的原文要点：

| 内容 | 原文要点 | 出处 |
|---|---|---|
| ROM 号 | 64 位：第 1 字节是家族码（DS18B20 为 28h），接着 48 位序列号，最后 1 字节 CRC | [4] 图 1、[5] |
| 位顺序 | 所有数据和命令都是**低位先发** | [5] |
| 搜索 | 复位 → 发 F0h → 每一位读两次（原码、反码）再写一位方向，共 64 位 | [4] 表 2 |
| 读到的两位 | 00：有 0 也有 1（分歧）；01：都是 0；10：都是 1；11：没有设备参与，**应终止搜索** | [4] 表 1 |
| 分歧时走哪边 | 位置 = 上次分歧点 → 走 1；位置 < 上次分歧点 → 和上次找到的 ROM 一样；位置 > 上次分歧点 → 走 0，并记下这个位置 | [4] 表 3 |
| 结束 | 本轮最后一个"走 0 的分歧点"成为下次的分歧点；为 0 说明已经是最后一个设备 | [4] 附录代码 |
| CRC | 多项式 X^8 + X^5 + X^4 + 1；搜到的 ROM 要校验 CRC，不对就不算找到 | [4]、[5] |
| 复位没有应答 | 没有设备，搜索失败 | [4] |
| 寻址 | 匹配 ROM 55h + 64 位 ROM 号；跳过 ROM CCh 同时寻址所有设备 | [5] |
| 转换 | 44h 开始转换；外部供电时，之后的读时隙在转换中读到 0、完成后读到 1 | [5] |
| 读暂存器 | BEh，读 9 字节，第 9 字节是前 8 字节的 CRC | [5] |
| 温度格式 | 16 位有符号，单位 1/16 °C（例：0191h = +25.0625 °C，FF5Eh = −10.125 °C，FC90h = −55 °C） | [5] 表 1 |
| 分辨率 | 配置寄存器（第 5 字节）的 R1R0：9/10/11/12 位；11 位时最低 1 位无意义，10 位时最低 2 位，9 位时最低 3 位 | [5] 表 2 |
| 上电值 | 温度寄存器上电是 +85 °C（0550h） | [5] |

### 怎么用

题目提供 1-Wire 接口头文件 `hal_onewire.h`（锁定），只有最底层的三个操作：复位（返回有没有应答）、写一位、读一位。

驱动要自己在上面实现：按字节读写（低位先）、CRC8、ROM 搜索（找出总线上所有设备）、对所有 DS18B20 同时启动转换、逐个读温度。很适合拆成"总线字节层 / CRC / 搜索 / DS18B20"几个模块。

### 规则

| 情况 | 应该怎样 | 依据 |
|---|---|---|
| 搜索全部设备 | 按 AN187 的算法反复搜索，直到最后一个；结果按找到的顺序存进调用方的数组 | [4] |
| 复位没有应答 | 返回"没有设备"，找到 0 个 | [4] |
| 搜索中途读到 11 | 本轮终止，返回"总线错误" | [4] 表 1 |
| 搜到的 ROM 号 CRC 不对 | 返回"CRC 错" | [4] |
| ★ 数组放满了还有设备 | 返回已找到的个数，并报告"还有更多"（不覆盖） | 我的选择 |
| ★ 家族码不是 28h 的设备 | 搜索结果里照常列出，但对它读温度返回"不是 DS18B20" | 我的选择 |
| 启动转换 | 复位 → 跳过 ROM（CCh）→ 44h | [5] |
| 等待转换完成 | 反复读一位，读到 1 才算完成 | [5] |
| ★ 等待的上限 | 头文件给出最多读多少次（例如 100000 次），超过返回"超时" | 与 W25Q 题的忙等待上限同理 |
| 读一个传感器 | 复位 → 匹配 ROM（55h + 8 字节 ROM 号）→ BEh → 读 9 字节 | [5] |
| 暂存器 CRC 不对 | 返回"CRC 错"，不修改输出 | [5] |
| 温度换算 | 原始值 × 100 ÷ 16，向零取整，单位 0.01 °C（例：25.0625 → 2506，−10.125 → −1012） | [5] 表 1；整数单位同 MPU6050 题 |
| 分辨率低于 12 位 | 先把无意义的低位清 0 再换算 | [5] 表 2 |
| ★ 读到 85 °C（上电值） | 照常返回，不当错误（真实温度也可能是 85 °C） | 我的选择 |
| 读 / 写的设备不存在（复位无应答） | 返回"没有设备" | [4] |
| 参数为 NULL | 返回"参数错误"，不碰总线 | 与前几道驱动题一致 |

**判卷方式**：隐藏测试带一条"假 1-Wire 总线"，可以挂多个假设备：读位时按真实总线做"线与"（任何一个设备拉低就是 0），搜索时不匹配的设备退出，直到下次复位。测试挂 1 个、3 个、8 个设备（包括 ROM 号只在最后几位不同的、家族码不同的），以及 CRC 错、搜索中途设备被拔掉（读到 11）、转换一直不完成、各分辨率和负温度。

**错卷（计划）**：分歧点比较写反（漏找设备）；高位先发；温度负数换算错（用无符号）；不校验暂存器 CRC。
