## 题 14：ISO-TP 传输层 isotp（协议，难度 3，多模块）

### 参照了什么

| 内容 | 原文要点 | 出处 |
|---|---|---|
| 帧类型 | 第 1 字节高 4 位：0 单帧、1 首帧、2 连续帧、3 流控 | [1]、[2] |
| 单帧 | 低 4 位是数据长度（经典 CAN 为 1–7），后面跟数据 | [1]、[2] |
| 首帧 | 低 4 位 + 第 2 字节组成 12 位总长度；后面 6 字节是数据 | [1]、[2] |
| 首帧长度为 0 | 表示后面 4 字节是 32 位长度（新版标准的扩展） | [2] |
| 连续帧 | 低 4 位是序号：第一个连续帧是 1，到 15 之后回到 0 | [2]（"rx.sn = 1"，"sn %= 16"） |
| 流控 | 低 4 位是状态：0 继续发送、1 等待、2 溢出；第 2 字节块大小，第 3 字节最小间隔 | [1]、[2] |
| 块大小 | 0 表示之后全部连续帧都不再等流控；大于 0 表示每发这么多帧等一次流控 | [1]、[2] |
| 最小间隔 | 00h–7Fh = 0–127 毫秒；F1h–F9h = 100–900 微秒；其他值保留，按 7Fh（127 毫秒）处理 | [2]（"fix wrong STmin values according spec"） |
| 接收方缓冲区不够 | 回流控"溢出"并放弃这次接收 | [1] SWS_CanTp_00318 |
| 序号不对 | 放弃这次接收 | [1] SWS_CanTp_00314 |
| 收到不认识的流控状态 | 放弃这次发送 | [1] SWS_CanTp_00317 |
| 收到流控"溢出" | 放弃这次发送 | [1] SWS_CanTp_00309 |
| 接收中又来一个单帧 / 首帧 | 放弃当前接收，按新的开始 | [1] 表 1 |
| 空闲时收到连续帧、流控 | 忽略 | [1] 表 1 |
| 不认识的帧类型 | 忽略 | [1] 表 1 |
| 首帧必须是满 8 字节 | 是 | [2]（"the first frame has to use the entire frame"） |

### 怎么用

★ **只做经典 CAN（8 字节）、普通寻址，不做 CAN FD 和 32 位长度**：最长 4095 字节。理由：这是车上最常见的用法，规则已经够复杂；32 位长度只在新版标准和 CAN FD 下才有意义。

★ **事件驱动，不自己计时**：收到一帧 CAN 就交给模块；超时（等流控的 N_Bs、等连续帧的 N_Cr）由调用方计时后通知模块；发送方的"最小间隔"由模块算好告诉调用方，调用方等够了再发。

模块分**接收**和**发送**两部分（很适合拆成接收、发送、帧格式三个模块）：
- 接收：喂一帧 → 告诉调用方"收完了一条消息 / 需要回一帧流控 / 出错了"；
- 发送：开始发一条消息（给出第一帧）→ 收到流控后一帧一帧取出连续帧和间隔 → 完成或出错。

### 规则：接收

| 情况 | 应该怎样 | 依据 |
|---|---|---|
| 单帧，长度 1–7 且不超过本帧实际字节数 | 收下，报告"收完一条" | [1]、[2] |
| ★ 单帧长度为 0 或超出本帧字节数 | 忽略 | [2] 的做法 |
| 首帧（必须满 8 字节），总长度 8–4095 | 存下前 6 字节，回流控"继续发送"（带上本端设定的块大小和最小间隔），等序号 1 的连续帧 | [1]、[2] |
| ★ 首帧不足 8 字节、总长度小于 8、总长度为 0（32 位扩展） | 忽略 | [2] 的做法；本题不支持 32 位长度 |
| 首帧总长度超过接收缓冲区 | 回流控"溢出"，不接收 | [1] |
| 连续帧，序号正确 | 存下数据；收齐就报告"收完一条"；每收满"块大小"个连续帧（块大小不为 0 时）就再回一帧流控"继续发送" | [1]、[2] |
| 连续帧序号不对 | 放弃这次接收，报告"序号错" | [1] |
| ★ 不是最后一帧的连续帧不足 8 字节 | 放弃这次接收，报告"格式错" | [2] 的做法 |
| 接收中又来单帧或首帧 | 放弃当前接收（计一次"被打断"），按新的处理 | [1] 表 1 |
| 空闲时收到连续帧 | 忽略 | [1] 表 1 |
| 流控帧、帧类型 4–F | 接收端忽略 | [1] 表 1 |
| 调用方通知"等连续帧超时" | 放弃这次接收，报告"超时" | [1] SWS_CanTp_00313 |

### 规则：发送

| 情况 | 应该怎样 | 依据 |
|---|---|---|
| 长度 1–7 | 发一个单帧，立即完成 | [1]、[2] |
| 长度 8–4095 | 发首帧（含前 6 字节），等流控 | [1]、[2] |
| 长度 0 或超过 4095，或上一条还没发完 | 拒绝 | — |
| ★ 发出的帧一律补满 8 字节，空位填 CCh | AUTOSAR 允许配置填充值；CCh 是常用值 | [1] 7.3.8 |
| 流控"继续发送" | 按块大小发连续帧（块大小 0 = 全部发完）；序号从 1 开始，15 之后回到 0 | [1]、[2] |
| ★ 块大小和最小间隔 | 以第一帧流控为准，之后的流控只看状态 | [2] 的默认做法；[1] 要求接收方每次给相同的值 |
| 最小间隔换算 | 00h–7Fh 毫秒；F1h–F9h 为 100–900 微秒；保留值按 127 毫秒 | [2] |
| ★ 间隔怎么告诉调用方 | 每个连续帧附带"发这一帧之前要等多少微秒"；收到流控后的第一个连续帧等 0 | 我的选择：最小间隔是两个连续帧之间的间隔 |
| 流控"等待" | 继续等下一帧流控 | [1]、[2] |
| 流控"溢出" | 放弃发送，报告"对方缓冲区不够" | [1] SWS_CanTp_00309 |
| 流控状态 3–F，或流控帧不足 3 字节 | 放弃发送，报告"流控错" | [1] SWS_CanTp_00317、[2] |
| 不在等流控时收到流控 | 忽略 | [1] 表 1 |
| 调用方通知"等流控超时" | 放弃发送，报告"超时" | [1] SWS_CanTp_00316 |

**判卷方式**：隐藏测试用自己写的帧生成器扮演对端：收发 1、7、8、9、62、63、4095 字节的消息（覆盖单帧、首帧、序号回绕 15→0），块大小 0 / 1 / 3，各种最小间隔（含保留值），等待、溢出、坏状态，序号跳号，接收中被新单帧打断，超时。

**错卷（计划）**：序号 15 之后回到 1；不按块大小停下等流控；保留的最小间隔当 0；接收端收到首帧不回流控。

## 题 15：SD 卡 SPI 模式初始化 sd_spi_init（驱动，难度 3）

### 参照了什么

ChaN《How to Use MMC/SDC》[3]、Linux 内核 SD 驱动 [4]（`include/linux/mmc/mmc.h`、`sd.h`、`drivers/mmc/core/sd_ops.c`、`drivers/mmc/host/mmc_spi.c`）。

| 内容 | 原文要点 | 出处 |
|---|---|---|
| 上电 | 片选和数据线保持高电平，先送 74 个以上时钟 | [3] |
| 命令格式 | 6 字节：01xxxxxx（40h + 命令号）、4 字节参数（高字节在前）、CRC7 + 结束位 1 | [3]、[4] mmc_spi.c |
| CMD0 | 复位进入 SPI 模式；期望回应 R1 = 01h（空闲） | [3]、[4] |
| CRC | SPI 模式下 CRC 默认不检查，但 CMD0 和 CMD8 必须带正确的 CRC | [3] |
| 回应等待 | 回应在 0–8 个字节内出现：一直发 FFh 并读，直到读到最高位为 0 的字节 | [3] |
| R1 各位 | bit0 空闲、bit1 擦除复位、bit2 非法命令、bit3 CRC 错、bit4 擦除序列错、bit5 地址错、bit6 参数错；bit7 恒为 0 | [4] mmc.h |
| CMD8 | 参数 000001AAh；回应 R1 后跟 4 字节，最低 12 位要回显 1AAh，否则这张卡不能用；回"非法命令"说明是 1.x 版卡 | [3]、[4] sd_ops.c |
| ACMD41 | 先发 CMD55，再发 CMD41；2.0 版卡参数带 HCS 位（40000000h），1.x 版卡参数为 0；反复发直到 R1 = 00h（初始化可能要几百毫秒） | [3]、[4]（超时 2 秒、每 10 毫秒一次） |
| CMD58 | 读 OCR（R1 后跟 4 字节，高字节在前）；bit30 = CCS：1 是大容量卡（SDHC/SDXC，按块号寻址），0 是标准容量卡（按字节地址） | [3]、[4] sd.h |
| CMD16 | 把块长度设为 512（标准容量卡需要） | [3] |
| 核对 | 按 CRC7 算法自己算：CMD0 的 CRC 字节 95h，CMD8 的 87h，与公认值一致 | 自己计算 |

### 怎么用

题目提供 SPI 接口头文件（锁定），两个函数：控制片选；发一个字节同时收一个字节。

驱动提供：初始化（识别卡的类型）、读一个 512 字节的块。

### 规则

| 情况 | 应该怎样 | 依据 |
|---|---|---|
| 上电 | 片选拉高，发 10 个 FFh（80 个时钟） | [3] |
| ★ 每条命令之前 | 拉低片选，先发 1 个 FFh | [3] 的示例做法（给卡留出准备时间） |
| ★ 每条命令都带正确的 CRC7 | 不只 CMD0、CMD8；所有命令都算 | 我的选择：一律带对的 CRC 最稳妥 |
| 等回应 | 最多发 8 个 FFh，读到最高位为 0 的字节就是回应 | [3] |
| ★ 8 个字节内没有回应 | CMD0 时报"没有卡"；其他命令报"无响应" | 我的选择 |
| ★ 每条命令之后 | 读完回应的全部字节后拉高片选，再发 1 个 FFh | [3] 的示例做法 |
| ★ CMD0 回应不是 01h | 最多重试 10 次，仍不对报"没有卡" | 我的选择：上电后第一条命令偶尔会失败 |
| CMD8 回"非法命令" | 当作 1.x 版卡继续 | [3] |
| CMD8 回 01h，但回显不是 1AAh | 报"电压不支持" | [3]、[4] |
| CMD8 其他回应 | 报"命令错" | — |
| ACMD41 | CMD55 + CMD41，2.0 版卡带 HCS、1.x 版卡不带，直到回 00h | [3] |
| ★ ACMD41 的次数上限 | 头文件给出（例如 1000 次），超过报"初始化超时" | 题目没有延时函数，按次数限制 |
| ★ 1.x 版卡的 ACMD41 回"非法命令" | 报"不支持"（那是老式 MMC 卡，本题不做） | 我的选择 |
| 2.0 版卡 | 发 CMD58，CCS = 1 记为"大容量卡"，否则"标准容量卡" | [3]、[4] |
| 标准容量卡和 1.x 版卡 | 发 CMD16（512），回应不是 00h 报"命令错" | [3] |
| 读块（CMD17） | 大容量卡参数是块号，标准容量卡参数是块号 × 512 | [3] |
| ★ 读块等数据起始标志 FEh | 最多读 1000 个字节（头文件给出），读到 FEh 后读 512 字节数据和 2 字节 CRC；读到 0000xxxx 形式的"错误标志"报"读出错" | [3] |
| ★ 数据的 CRC16 | 不校验（SPI 模式默认关闭 CRC），但 2 个 CRC 字节必须读掉 | [3] |
| 没初始化成功就读 | 报"参数错误"，不碰总线 | 与前几道驱动题一致 |
| 参数为 NULL | 报"参数错误"，不碰总线 | 同上 |

**判卷方式**：隐藏测试带一张"假 SD 卡"，按 SPI 时序逐字节模拟：可以设成 2.0 大容量卡、2.0 标准容量卡、1.x 版卡、MMC 卡、电压不支持的卡、没插卡；可以让回应晚到几个字节、让 ACMD41 要等很多次才就绪；会检查每条命令的 CRC7、片选是否在命令前后正确拉低拉高。

**错卷（计划）**：CMD8 的 CRC 写错；大容量卡也按"块号 × 512"给地址；ACMD41 不带 HCS 位；只等 1 个字节就判定没有回应。

## 题 16：AT 指令响应解析 at_parser（状态机，难度 3）

### 参照了什么

ITU-T V.250（2003-07）[5]、3GPP TS 27.007 Rel-19 [6]。

| 内容 | 原文要点 | 出处 |
|---|---|---|
| 响应的种类 | 信息文本和结果码两种；结果码又分最终、中间、主动上报（例如 RING） | [5] 5.7.1 |
| 格式（默认 V1） | 信息文本：`<CR><LF>文本<CR><LF>`；结果码：`<CR><LF>结果<CR><LF>` | [5] 表 3 |
| 最终结果码 | OK、ERROR、NO CARRIER、NO DIALTONE、BUSY、NO ANSWER（CONNECT 是中间结果码，RING 是主动上报） | [5] 表 1 |
| 扩展结果码 | 以 `+` 开头，格式 `+名称: 值`（冒号后一个空格） | [5] 5.7.2 |
| 回显 | 默认开启（E1）：模组会把收到的命令原样发回来 | [5] 6.2.4 |
| +CME ERROR | 打开 +CMEE 后，与模组功能有关的错误用最终结果码 `+CME ERROR: <err>` 代替 ERROR；+CMEE=1 时 err 是数字，=2 时是文字；语法错误、参数错误仍然回 ERROR | [6] 9.1 |
| 错误码例子 | 3 = operation not allowed，4 = operation not supported，10 = SIM not inserted，11 = SIM PIN required | [6] 9.2.1 |
| +CSQ | 回应 `+CSQ: <rssi>,<ber>`；rssi：0 = −113 dBm 或更低，1 = −111 dBm，2–30 = −109…−53 dBm，31 = −51 dBm 或更高，99 = 未知；ber：0–7 或 99 = 未知 | [6] 8.5 |
| 同一个前缀两种身份 | 例如 `+CREG:` 既是 AT+CREG? 的信息文本，也是网络状态变化时的主动上报 | [6] 7.2 |

### 怎么用

调用方发出一条命令时告诉解析器"这条命令的信息文本以什么开头"（例如 AT+CSQ 对应 `+CSQ`）；之后把串口收到的每个字节交给解析器。解析器按行切分，每次告诉调用方：收到一行信息文本 / 收到主动上报 / 命令结束（OK、ERROR、+CME ERROR 带错误码）。另外提供一个解析 +CSQ 的小工具函数。

### 规则

| 情况 | 应该怎样 | 依据 |
|---|---|---|
| ★ 行的切分 | 遇到 CR 或 LF 就结束一行；空行忽略（这样 `<CR><LF>` 和只有 LF 的模组都能处理） | [5] 表 3 的推论 |
| ★ 一行太长（超过头文件给的上限，如 128 字节） | 丢掉这一行直到行尾，报告"行太长" | 我的选择 |
| ★ 命令进行中，收到与所发命令完全相同的一行 | 当作回显，忽略 | [5] 6.2.4 |
| 命令进行中，收到 OK | 报告"命令成功"，命令结束 | [5] |
| 命令进行中，收到 ERROR | 报告"命令失败"，命令结束 | [5] |
| 命令进行中，收到 `+CME ERROR: <数字>` | 报告"命令失败"并给出错误码，命令结束 | [6] 9.1 |
| ★ `+CME ERROR:` 后面是文字（+CMEE=2） | 同上，错误码记为 −1 | 我的选择：不维护文字错误表 |
| ★ NO CARRIER、BUSY、NO ANSWER、NO DIALTONE | 报告"命令失败"并标明是哪一种，命令结束 | [5] 表 1：它们都是最终结果码 |
| 命令进行中，收到以这条命令的前缀开头的行 | 是信息文本 | [6] |
| ★ 命令进行中，收到以 `+` 开头但前缀不同的行，或 RING | 是主动上报（夹在命令中间的 URC） | [5] 5.7.1、[6] 的推论 |
| ★ 命令进行中，收到其他行 | 是信息文本（例如 AT+CGSN 回的是一串数字，没有前缀） | 我的选择 |
| ★ 没有命令时，收到以 `+` 开头的行或 RING | 是主动上报 | [5] 5.7.1 |
| ★ 没有命令时，收到 OK、ERROR 等其他行 | 忽略（多半是上一条命令超时后才到的残留） | 我的选择 |
| ★ 上一条命令没结束又要发新命令 | 拒绝 | 我的选择：AT 是一问一答 |
| ★ 调用方通知超时 | 当前命令结束，报告"超时" | 题目没有计时功能 |
| 解析 +CSQ | 从 `+CSQ: <rssi>,<ber>` 取出两个数；格式不对或数值不在 0–31/99、0–7/99 范围内返回失败；另给 rssi 换算 dBm（−113 + 2 × rssi，99 返回"未知"） | [6] 8.5 |

**判卷方式**：隐藏测试模拟一个 4G 模组的输出：有回显和无回显、只有 LF 的换行、+CSQ / +CREG? / AT+CGSN 的正常回应、命令中间夹着 RING 和 +CREG 主动上报、+CME ERROR 数字和文字两种格式、NO CARRIER、超长行、超时后才到的残留 OK、字节被拆得很碎地喂进来。

**错卷（计划）**：+CREG 主动上报在 AT+CREG? 进行中被当成上报（应是信息文本）；把回显当成信息文本；+CME ERROR 不当最终结果码（命令一直不结束）；rssi 换算差一档。
