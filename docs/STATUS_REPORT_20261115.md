## 三、复测里没过的 19 次，执行时具体发生了什么

复测 36 次里没过 19 次：mpu6050_drv_idf 6 次、rmt_pulse_meter 6 次、max30102_temp 3 次（都是 none）、mpu6050_drdy 2 次、max30102_fifo 1 次、ledc_pwm 1 次。

其中 **9 次是在第 1–2 次尝试就被诊断为"硬件或接线问题"而停下的**，剩下的机会没用。这 9 题的标准答案前一天都在同一块板上通过（`check-board-tasks --board` 全部符合预期），接线是好的，所以这 9 个诊断全是误诊。下面逐类还原。

### 3.1 mpu6050_drdy（数据就绪中断）：2 次误诊为"INT 线断了"

**发生了什么**：采集启动后 2 秒内一组数据都没收到。诊断 Agent 看到"寄存器都配置对了，但中断一次没来"，判为 INT 线没接通，叫人去查线，运行停下。

**真正的原因**：Agent 把 MPU6050 的 INT_PIN_CFG 写成了 `0xB0`，以为 bit7 置 1 是"高电平有效"；其实 bit7 = 1 是**低电平有效**（标准答案写的是 `0x30`）。中断脚于是平时为高、数据就绪时被拉低并锁存，而代码等的是**上升沿**——锁存的低电平要等读寄存器才会恢复，读寄存器又要等中断，互相等，永远等不到。

6 次运行逐一核对：

| 运行 | INT 极性 | 等的边沿 | 结果 |
|---|---|---|---|
| none 1 | 低有效 0xB0 | 下降沿 | 通过（自己前后一致） |
| none 2、full 1、full 2 | 高有效 0x30 | 上升沿 | 通过 |
| **none 3、full 3** | **低有效 0xB0** | **上升沿** | **卡死** |

**更值得注意的**：诊断 Agent 在证据里写的是"INT_PIN_CFG=0xB0 高有效推挽锁存"——和编码 Agent 犯了同一个错；测试 Agent 写的测试也在断言"INT_PIN_CFG 等于 0xB0"。三个 Agent 用同一个模型，带着同一个知识盲点，于是"互相印证"了一个错误结论（问题 9）。

### 3.2 rmt_pulse_meter（RMT 测脉冲）：3 次误诊为"跳线没接"，6 次全没过

**发生了什么**：测量带信号的方波时，接收全部超时（`ESP_ERR_TIMEOUT`），表现和"完全没信号"一模一样。诊断 Agent 据此判为 GPIO6→GPIO7 的跳线没接。

**真正的原因**：被测信号是一个**持续不断的方波**，不会自己"结束"。ESP-IDF 的 RMT 接收默认要等到信号空闲超过设定时间才算收完一段；方波一直在跳，永远等不到空闲，于是超时。标准答案打开了"分段接收"（`flags.en_partial_rx = 1`），注释写着"连续方波不会自己结束，必须分段接收"。

逐次核对：**12 次运行（基线 6 + 复测 6）里 10 次没打开分段接收**；打开了的 2 次又有别的错（连续测两次、反初始化后重测没过）。规则库里 16 条 RMT 规则没有一条讲这件事（问题 10）。

### 3.3 max30102_temp（片内测温）：none 3 次全没过，full 3 次全过

**发生了什么**：none 的 3 次读出来的温度都是 0.00 °C（TINT=0x00、TFRAC=0x00），其中 2 次诊断为"这颗 MAX30102 温度功能坏了，换模块"，运行停下。

**真正的原因**：Agent 用"轮询 TEMP_EN 位，等它自动清零就算测完"来判断测温结束。这块模块的 TEMP_EN 写进去马上就清零了，Agent 以为测完，立刻去读，读到的是还没出数的 0。正确做法是打开 DIE_TEMP_RDY 中断，等它置位再读——规则库里正好有这条（R-MAX-008，引自 MAX30102 数据手册）。

逐次核对：none 的 3 次都是"轮询 TEMP_EN"，**full 的 3 次都按 R-MAX-008 等 DIE_TEMP_RDY，3 次全过**。这是规则库价值最清楚的一个例子。

### 3.4 max30102_fifo：1 次误诊为"芯片是假货"

**发生了什么**：往 LED1_PA 写 0x24，读回来是 0x04；诊断 Agent 判为"该寄存器异常，疑似克隆芯片，换一颗"。

**真正的原因**：Agent 把寄存器地址写错了——它把 LED1_PA 当成 0x0B、LED2_PA 当成 0x0C，而 MAX30102 上它们是 0x0C、0x0D（像是记成了老型号 MAX30100 的地址）。所以"LED1 读回 0x04"读的根本是另一个寄存器。这题 full 3 次全过（规则库里有寄存器地址）。

### 3.5 mpu6050_drv_idf：6 次全没过，而且全是"自检过松"

**发生了什么**：隐藏测试在 ±8 g 量程下读加速度，6 次读出来都是约 **4.05 g**（应为 1 g），恰好是 4 倍；而 Agent 自己写的测试全部通过，流程判"通过"。

**最可能的原因**：4 倍正好是 ±8 g 和 ±2 g 的比例，说明读到的是改量程之前那一组数据。标准答案在配置完量程后等 50 ms"等第一组数据就绪"再返回；Agent 的初始化配完就返回，隐藏测试紧接着读，读到的还是旧量程下的样本，却按新量程换算。Agent 自己的测试要么只测默认量程，要么初始化后隔了一会儿才读，所以没抓到（问题 11）。
（这一条是根据倍数、标准答案的等待和 Agent 代码的对比推断的，没有单独上板复现。）

## 四、这些问题背后的几个根本原因

**问题 8：误诊为硬件问题就停。** 诊断 Agent 遇到"读数全 0 / 一直超时 / 中断不来"这类现象，倾向于归到硬件；而平台把"硬件问题"当成终点，直接停下等人。评测里没人回应，就算没过；软件里也没有"我查过了，接线没问题，继续"的按钮。平台其实知道接线是好的（接线实测确认、标准答案在本板上通过过），但没用上这个信息。

**问题 9：同一个模型当三个角色，交叉验证失效。** 编码、测试、诊断都是 deepseek-flash。3.1 里三个 Agent 都把 0xB0 当成"高有效"，测试照着错的理解写、诊断照着错的理解判——"多 Agent 互相检查"在共同盲点上不起作用。这和 MAST 论文"多 Agent 的失败多来自系统设计"的结论一致，也是答辩时可以主动讲的局限和改进方向（例如诊断换另一个档位或另一家模型、或者让平台用客观测量去核对诊断结论）。

**问题 10：规则库缺关键知识。** RMT 分段接收、MPU6050 INT 极性位、改量程后要等新数据——这几条规则库里都没有。**但要注意**：这几条是我对照**测试题的标准答案**才看出来的，如果现在补进规则库再复测，就等于"看了答案再考"，测试题的对比就不干净了。可以补，但要么方案书里明确披露，要么等决赛换新题再验证。

**问题 11：Agent 自己的测试不够严。** 修正循环修好以后，更多代码能上板，"自检过松"（流程判过、隐藏测试没过）成了第二大问题：时序类、边界类的情况 Agent 自己想不到要测。

**问题 5（调优题太简单）：** 调优题 20 次过 19 次，调度器只攒到 10 条成绩、经验库为空。"在调优题上学、在测试题上用"这一步基本没学到东西，所以 full 比 none 好的部分主要来自规则库。

## 五、需要你拍板的事

1. **误诊为硬件问题时怎么办**（问题 8）。我建议：诊断说硬件时，平台先查接线实测记录，已确认就不停、改按代码问题继续，并写明原因；查不到才停；软件里加"接线没问题，继续"按钮。改完要再测一次才能看出效果（约 8 元、2.5 小时），而测试题已经量过两次，第三次要在方案书里如实写明。
2. **诊断 Agent 要不要换档位或换模型**（问题 9）。例如诊断用 strong 档（第 31 条本来就定了诊断用 strong，评测时为了省钱统一成了 fast）。
3. **补不补那几条规则**（问题 10），补的话怎么披露。
4. **接下来时间怎么分配**：初赛 11/20 交，还剩 5 天；方案书（≥ 5000 字）、PPT、视频都还没开始。我的建议是：问题 8 改完测一次就停止调优，把现有数据如实写进方案书——"修好了一个让修正循环失效的程序错误，花费减半、自检过严归零；通过率有提升但样本小不显著；发现了同模型交叉验证失效等局限"，这本身就是一份有说服力、经得起追问的工程报告。
