## 一、一次完整运行是什么样（以 Modbus 从机为例）

```
需求 + 接口头文件
   │
   ▼
【规划 Agent】把任务拆成模块 → dag.json
   │    例：crc（CRC 计算）、frame（帧检查与组装，依赖 crc）、slave（分发与功能码，依赖 frame）
   │    引擎检查：无环、id 不重复、文件不重叠、公共函数都有人负责；不合格让它重做（最多 2 次）
   ▼
（可选）【人工确认】开了 --human-review 才停下来等你点头
   ▼
【按依赖逐层推进，没有依赖关系的模块同时进行】
   每个模块：
     ① 调度器选一个编码 Agent（fast 或 strong），得分明细记进事件
     ② 编码 Agent 写实现  ∥  测试 Agent 只看需求写测试（两者同时进行）
     ③ 阅卷机判定（本模块 + 已完成的依赖模块，L1–L5）
     ④ 没过 → 诊断 Agent 判断错在代码还是测试 → 交给对应的 Agent 修改 → 再判定
        （变差就退回到最好的那次；最多 6 次）
     ⑤ 过了 → 审查 Agent 看一遍（只提示，最多触发 1 次额外修改，不能否决通过）
     ⑥ 模块文件复制进"集成目录"
   ▼
【集成判定】所有模块合在一起，跑全部 Agent 测试
   ▼
交付代码 + 验证报告
```

## 三、五个评测配置的区别

| 配置 | 几个 Agent | 怎么分配 | 修正 | 诊断 | 审查 |
|---|---|---|---|---|---|
| b1 | 1 | — | 不修 | 无 | 无 |
| b2 | 1 | — | 报错直接回喂，最多 3 轮 | 无 | 无 |
| b3 | 多 | 一次一个模块，固定用第一个编码 Agent | 有 | 有 | 无 |
| b4 | 多 | 模块并行，编码 Agent 轮流 | 有 | 有 | 无 |
| full | 多 | 模块并行，smart 打分 | 有 | 有 | 有 |
| b5 | 1 | — | 每次从头重写（不带报错），直到通过或花完与 full 相同的 token | 无 | 无 |

（阶段 4 再给 full 加上升级阶梯和经验库，并加 3 个消融配置。）

**smart 打分**（ARCHITECTURE §7，每次分配都会把每一项写进事件，你能看到"为什么选它"）：

```
得分 = 历史成功率 − 0.3 × 相对成本 − 0.2 × 当前负载 + 0.5 × 探索奖励
```
- 历史成功率：这个 Agent 在这类题上 (成功次数 + 1) ÷ (尝试次数 + 2)，没数据时是 0.5；
- 相对成本：它的平均花费 ÷ 候选者里最贵的那个；
- 当前负载：它手上正在做的模块数 ÷ 并发上限；
- 探索奖励：用得越少的 Agent 奖励越高，避免一直只用一个（多臂老虎机里的 UCB 思路，调研报告 W8）。

## 四、规划 Agent 和诊断 Agent 的提示词草案

### 4.1 规划 Agent（prompts/planner.md）

```
你是嵌入式软件架构师。请把下面这个 C 模块的需求拆成若干"实现单元"（下称模块），
交给多名工程师分别实现。

## 你会收到
- 需求文档；
- 公共接口头文件（只读，任何模块都不能修改）。

## 拆分原则
1. 模块要小而内聚，模块之间通过少量函数交互。简单需求只拆成 1 个模块即可，不要为拆而拆；最多 5 个模块。
2. 公共头文件里的每一个函数，必须由且只由一个模块负责实现（写进它的 provides）。
3. 模块之间的内部接口，写在 interface 字段里：给出内部头文件的路径和其中每个函数的原型。
   提供接口的模块负责写这个头文件，使用接口的模块把它列进 depends_on。
4. depends_on 只能填其他模块的 id，不能出现循环依赖。
5. 每个模块的 files 只能是 src/ 下的 .c 或 .h 文件，不同模块的文件不能重叠。
6. 每个模块写 2–5 条 acceptance：可以直接写成单元测试的验收要点，必须来自需求文档，不要自己发明需求。
7. task_type 只能是 data_structure、protocol、state_machine、driver 之一。

## 输出格式
只输出一个 ```json 代码块，内容为：
{
  "modules": [
    {
      "id": "crc",
      "title": "CRC-16/MODBUS 计算",
      "task_type": "protocol",
      "files": ["src/mb_crc.c", "src/mb_crc.h"],
      "provides": [],
      "interface": {"src/mb_crc.h": ["uint16_t mb_crc16(const uint8_t *data, size_t len);"]},
      "depends_on": [],
      "acceptance": ["\"123456789\" 的 CRC 为 0x4B37", "len 为 0 时返回 0xFFFF"]
    }
  ]
}
```

### 4.2 诊断 Agent（prompts/diagnoser.md）

```
你是嵌入式软件的测试与调试专家。某个模块没有通过判定器检查，请判断错在哪里，并给出修改指令。

## 你会收到
- 需求文档、公共接口与本模块的内部接口；
- 本模块的实现代码和单元测试代码；
- 判定报告（首个失败层、报错、日志摘录）；
- 本模块历次的错误签名。

## 判断步骤
1. 先对照需求文档，逐条核实测试的期望值是否正确；
2. 再看实现是否符合需求；
3. 如果错误签名连续出现同一个，说明上次的修改方向不对，必须换一个思路。

## 责任（blame）只能取以下之一
- code：实现不符合需求，测试是对的；
- test：测试本身错了（期望值不对、用法不对、违反约束），实现是对的；
- interface：模块之间的接口设计有问题，只改一边修不好；
- spec：需求文档本身有歧义或矛盾；请按最合理的理解给出修法，并说明歧义在哪里。

## 输出格式
只输出一个 ```json 代码块：
{
  "blame": "code",
  "summary": "一句话说明根因",
  "instructions": "可以直接执行的修改步骤：指明文件、函数和要改成什么；不要整段重写代码",
  "confidence": 0.8
}
confidence 是 0 到 1 之间的数，表示你有多大把握。
```

## 五、单元测试（全部用假 LLM，不联网）

- 规划结果检查：有环、id 重复、文件重叠、公共函数没人负责、路径不在 src/ 下，都能识别；不合格会让规划 Agent 重做，最多 2 次；
- **测试 Agent 收到的消息里没有任何 src/*.c 的内容**（验收第 2 条）；
- 依赖关系：依赖模块完成后才开始；没有依赖的模块确实同时运行（看事件时间戳）；
- 诊断分派：blame = code 交给编码 Agent，test 交给测试 Agent；
- 回滚：这次比上次差，下一轮从最好的那次开始；
- 四种调度策略的分配结果；smart 的得分明细与公式一致；
- 审查：只在客观层全过之后运行；最多触发 1 次额外修改；
- 人工节点：评测模式自动跳过，`--human-review` 时停下等待；
- b5 的 token 预算取自同一实验里 full 的平均值；
- 原有的隔离测试扩展到多 Agent：所有角色的消息、运行目录里都没有隐藏测试的内容。
