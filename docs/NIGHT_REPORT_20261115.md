## 1. 通过率低的原因（回答"是不是程序错误"）

基线（results/final_before，54 次，14.74 元）的 33% 就是交付代码的真实水平：判定用隐藏测试直接跑交付的代码。程序错误的影响在于修正循环——
36 次多 Agent 运行里 **21 次从头到尾没拿到过一次上板反馈**（每次都卡在测试文件编译不过），多 Agent 实际退化成了"写一次就交"，
所以三种配置通过率几乎一样。修好以后能到多少，要等测试题复测才知道。

## 3. 修正循环的故障注入演练（tests/test_repair_sim.py）

参照 MAS-FIRE（2026，多 Agent 故障注入）和 Hypothesis 的状态机测试：模拟一个"世界"（驱动、测试各自可能编译不过 / 逻辑错 / 正确），
假 Agent 按随机种子修好、改坏、乱回、不交文件，跑真实的分派代码（固定流程和工作流解释器各一遍），检查 8 条不变量：会停、编译错交对人、
诊断结论交对人、反馈送到、判通过时真的过了、不抛异常、判没过时机会用完、最后一次检查后不再叫 Agent。

- 300 个种子 × 2 种流程：没有违反；
- 把第 122 条修掉的旧错误装回去：几秒内报出来（演练本身有效）；
- 变异测试新加 3 个目标：修正循环分派 41%、解释器 71%、工具参数 83%；存活的逐个看过，主要是事件里的序号、费用记账、经验库这些
  不影响"交给谁"的地方，以及等价变异体（例如最后一次循环里 break 换 continue）。

## 5. 需要你拍板的事

**⓪ 调优题太简单（最重要）。** 5 道调优题大多是难度 1–2，20 次过了 19 次，出现了天花板：调度器只攒到 10 条成绩、经验库是空的，
"在调优题上学、在测试题上用"这一步几乎没学到东西。可选：
- A. 照原计划直接复测测试题（none、full 各 3 次，上限 12 元），方案书如实写"调优题偏简单、调度和经验库学到的很少"；
- B. 调优题每题多跑几次（比如再 3 次），多攒成绩，再复测；
- C. 加几道难度 3 的调优题（要写题，耗时长，不推荐在初赛前做）。
我倾向 A：今晚的主要收获是修好了修正循环，复测最能看出它的效果；调度对比本来就定在决赛做。

**① 误诊为"硬件问题"时运行直接停下。** 评测里没人回答，就算没过；软件里也没有"我查过接线没问题，继续"的按钮。
可选：加这个按钮，评测时自动按"接线已确认"继续当代码问题处理；或者先不动。

**② 诊断 Agent 推理写满上限、一个字没回**（11/14 ledc_pwm 一次运行里连续 3 次，各 65536 token）。可选：把诊断 Agent 的输出上限
从 65536 降到 16384（这次正常的诊断最多用了 1 万出头）；改了算 Agent 新版本。

**③ 编码 Agent 读整页手册让上下文膨胀**（规则库配置下单次 130k–240k token）。可选：修改轮里只保留最近一次读的手册页，旧的换成一句摘要；
省钱，但可能让 Agent 少看到一些资料。

**④ ledc_pwm 在规则库配置下 3 次全没过、在无规则库配置下 3 次全过。** 记录里看到的原因有测试写法问题和诊断写满上限，但不排除某条 LEDC
规则有误导。可选：你明早花几分钟看一下知识库里 LEDC 的规则（规则是平台数据，不是隐藏测试，可以看）。
